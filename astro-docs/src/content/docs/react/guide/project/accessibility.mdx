title: Accessibility scope
description: What keyboard and screen-reader support Keystone Dashboard Layout for React actually provides — and what it deliberately doesn't (yet).
---

Same scope and reasoning as the Vue port's own
[Accessibility scope](/vue/guide/project/accessibility/) — this page
documents this package's own implementation specifically, confirmed
directly against `GridItem.tsx`'s own source, not assumed from feature
parity claims alone.

## What's implemented

### Keyboard move and resize

Every non-static, editable `GridItem` is keyboard-focusable
(`tabIndex={0}`) and operable:

- **Arrow keys** move it by one grid unit, if it's draggable.
- **Shift + arrow keys** resize it by one grid unit, if it's resizable.

Each keypress is treated as a complete, atomic gesture — implemented as
a synthetic `dragstart` immediately followed by `dragend` (or
`resizestart`/`resizeend`), the same two calls a real mouse gesture's
start and release would produce, so `GridLayout`'s own compaction/
collision/`multiSelect` group-move handling applies identically
regardless of which input method triggered the change.

**Works with `multiSelect`'s group move/resize too** — arrow-key/
Shift+arrow movement on a focused, *selected* item moves/resizes every
other selected item by the same delta, the same as a mouse/touch drag
already does. See [Multi-select & group move/resize](/react/examples/multi-select-group-move-resize/).

**Deliberately scoped to single-unit steps**, not a full
[WAI-ARIA grid](https://www.w3.org/WAI/ARIA/apg/patterns/grid/) or
[application](https://www.w3.org/WAI/ARIA/apg/patterns/) widget pattern.
This library isn't a traditional data grid — it's a freeform draggable
canvas — so the full APG grid pattern doesn't map cleanly onto it.

### Screen reader support

- Each interactive item gets `role="group"` and
  `aria-roledescription` (default `"Draggable, resizable item"`), so a
  screen reader announces it as something other than a plain, silent
  `<div>`.
- `aria-describedby` points to a visually-hidden instructions string
  ("Press arrow keys to move." / "Press shift plus arrow keys to
  resize.", each only included if that action actually applies to the
  item) — discoverable on focus, not a mandatory upfront announcement.
- A visible focus outline, so a keyboard user can actually see which
  item currently has focus.

### A deliberate, non-obvious design decision worth calling out

Keyboard move/resize **ignores `dragAllowFrom`/`dragIgnoreFrom`/
`resizeIgnoreFrom`** entirely — confirmed directly in `handleKeyDown`,
which reads only `resolvedDraggable`/`resolvedResizable` and never
touches any of the three. Those fields restrict which DOM element a
*mouse* drag/resize gesture can originate from (see
[Drag allow/ignore elements](/react/examples/drag-allow-ignore-elements/)
and [Custom drag handle](/react/examples/custom-drag-handle-close-button/)),
which is a concept that doesn't map onto keyboard interaction at all. A
keyboard user who focuses the item gets full move/resize access
regardless of whether a mouse user is restricted to a specific handle —
intentional, matching the Vue port's own identical reasoning:
restricting keyboard users *further* than mouse users, just because a
mouse-specific UI affordance (a drag handle) exists, would be the wrong
direction for an accessibility feature to take.

### Maximize and restore

The built-in maximize button (`showMaximizeButton`) is a real
`<button type="button">`, so it is reachable with Tab and operable with
Enter or Space. Its text is a visually-hidden label that reads
"Maximize" and, while its item is the maximized one, "Restore" — both
overridable through `ariaLabels` (`maximizeButton`/`restoreButton`).

**Escape restores.** With focus anywhere inside the grid, Escape puts
every item back — unless something inside the item (a dropdown or a
dialog closing, say) already handled that key press, in which case it is
left alone. Escape does nothing when no item is maximized, and a focus
outside the grid does not trigger it.

**Clicking the button moves focus onto it.** Safari does not focus a
button when it is clicked, so without this a mouse user there would
maximize an item and find Escape dead until they tabbed into the grid.
The button keeps focus when the same click restores the item. Maximizing
through `maximize()` or the `maximizedItem` prop leaves focus where it
was: the grid does not take it from something else on the page.

While an item is maximized it is neither draggable nor resizable, so it
drops out of the tab order and loses its group role and keyboard
instructions like any other item that can't be moved; the other items
are hidden (`display: none`), so they are skipped by Tab and by screen
readers until you restore. See [Maximize and restore](/react/examples/maximize/).

### Localizable ARIA strings

The close button's label, `aria-roledescription`, and the keyboard
move/resize instructions are all overridable rather than hardcoded
English literals — see [Localizable ARIA strings](/react/examples/aria-labels/)
and [ARIA labels](/react/api/interfaces/aria-labels/). The maximize
button's two labels are overridable the same way.

## What's not covered (tracked, not silently ignored)

- **No roving-tabindex grid navigation.** Tabbing moves through items in
  DOM order, the same as any other focusable elements on a page —
  there's no arrow-key-based "move focus to the item above/below/left/
  right" navigation independent of actually moving the focused item.
- **No keyboard equivalent for the drag-from-outside / drag-between-grids
  examples** ([Drag, drop from outside](/react/examples/outside-drag-drop/),
  [Drag, drop from grid to grid](/react/examples/cross-grid-drag-drop/)) —
  those are consumer-level example code, not library internals.
- **Not independently audited against WCAG success criteria** or run
  through an automated tool (axe, Lighthouse, etc.).
- **Color contrast and the default item styling generally** haven't
  been reviewed — `GridItem`'s content is unstyled by default, so this
  is mostly a consumer responsibility.

## Verifying this

`GridItemKeyboard.spec.tsx` covers: focus attributes present/absent
correctly based on static/edit-mode state, arrow-key movement
(including bounds clamping and the `isDraggable: false` guard),
shift+arrow resize (including `minW`/`minH` clamping and the
`isResizable: false` guard), and that non-arrow keys and disabled
edit-mode are correctly no-ops.
