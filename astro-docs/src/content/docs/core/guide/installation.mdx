```sh
npm i keystone-dashboard-layout-core
```

Works with `import`, `require`, and TypeScript's own type resolution —
the package ships ESM, CJS, and its own `.d.ts` types, so no extra
`@types` package is needed either way.

```ts
import { collides, compactLayout, getBreakpointFromWidth } from 'keystone-dashboard-layout-core';
```

## The cross-grid-registry subpath

Everything above comes from the package's own main entry point. One
piece is deliberately **not** re-exported there: the cross-grid
registry — the runtime coordination point multiple grids on the same
page use to recognize each other for drag-and-drop between them. It's
a stateful, singleton-style module tied to component mount/unmount,
not a pure calculation the way everything else here is, so it's kept
as its own, explicit subpath import instead of bundled into the main
one:

```ts
import { registerCrossGridZone } from 'keystone-dashboard-layout-core/gridlayout/helpers/cross-grid-registry';
import type { ICrossGridZone } from 'keystone-dashboard-layout-core/gridlayout/interfaces/cross-grid.interfaces';
```

Only worth reaching for directly if you're building a new framework
integration from scratch — the Vue and React packages already wire this
up internally for their own `allowCrossGridDrag` prop.

## The types-only subpath

The package also exposes a types-only `./types/*` subpath, mapped to the
declaration files under `dist/types/`. It has no runtime code behind it,
so it can only be imported with `import type`. The published `.d.ts`
files of the Vue and React packages refer to core's types through this
subpath (`keystone-dashboard-layout-core/types/...`), which is what lets
your editor resolve every type those packages re-expose without a build
step or a path alias on your side. You rarely need to write one of these
imports yourself; the main entry point re-exports the same types.
