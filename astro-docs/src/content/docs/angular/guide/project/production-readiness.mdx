## Runtime dependencies

**Correction to this page's own earlier phrasing**: this package is **not** zero-runtime-dependencies the way Vue and React are. Confirmed via a direct read of `package.json`'s own `dependencies` field: `@keystone-dashboard-layout/core` (workspace, shared with Vue/React) **and `tslib` (^2.6.0)** — a real, external npm dependency, not just a workspace reference. `tslib` is an extremely common, small (a few KB), near-universal helper library for compiled TypeScript/Angular output — not a cause for concern in practice — but the previous "zero runtime dependencies... the Vue and React packages use" phrasing on this page was factually imprecise for this specific package and has been corrected here.

## Build & packaging

- **Bundle size** — now substantially measured, not assumed. The actual runtime code a consumer's bundler imports (`dist/keystone-dashboard-layout-angular/fesm2022/keystone-dashboard-layout-angular.mjs`) is **204.24 KB raw / 50.88 KB gzip** — meaningfully larger than React's own 17.97 KB gzip bundle, consistent with Angular's own decorator/DI metadata overhead. Separately: this package's own `check:bundle-size` script has a real, confirmed methodology issue, not just an unverified budget — it sums the gzipped size of *every file* in the whole `dist/keystone-dashboard-layout-angular/` output directory (its own top comment already acknowledges this coarser approach), which includes the packaged `.tgz` tarball, `README.md`, `LICENSE`, `package.json`, and every `.d.ts` type-declaration file (measured at **114.61 KB raw** across 10 files, dominated by `grid-layout.component.d.ts` at 50.90 KB and `grid-item.component.d.ts` at 36.36 KB — both carrying substantial JSDoc comment text into the emitted declarations) alongside the real code. None of those extra files reflect what actually ships to a browser at runtime. The script's own total (precisely measured for the four largest contributors, estimated for the rest) comes to roughly **~97 KB gzip**, still comfortably under the script's own `BUDGET_KB = 150` placeholder — but the *number itself* is measuring "everything in the npm tarball" rather than "runtime bundle size," which is worth fixing (e.g. pointing at just the `fesm2022/` output) before tightening the budget or making this check blocking.
- **`check:package-install` (pack-and-install smoke test)** — still genuinely unverified: `ci.yml` keeps this `continue-on-error: true` since the script's own assumptions about `ng-packagr`'s generated `package.json`/`exports` shape haven't been checked against a real build. Not resolved in this pass.
- **The library build itself** — confirmed working (`ng-packagr`), since the bundle-size measurement above required a real, successful `dist/` build to already exist.

Branch protection and repository secrets aren't checkable from source.

## Testing depth

Confirmed, not just "not yet checked": this package has **no e2e suite** — no Playwright config, and `ci.yml`'s own `e2e` job doesn't run for it at all (turbo skips any package without a `test:e2e` script, and this one deliberately has none — see `package.json`'s own `_comment_scripts`). Karma's own project-scoped config (`angular.json`'s `test` architect target, `karma.conf.js`) is present in the repository as a possible foundation for a future browser-flow e2e layer, but isn't wired up or run today. See [Testing philosophy](/angular/guide/project/testing/) for the fuller picture — unit/component coverage itself (Jest + jest-preset-angular) is real and CI-enforced; this gap is specifically about end-to-end browser testing.

## Accessibility

Confirmed via a direct read of `grid-item.component.ts`'s own source, not just the package's introduction claiming parity: keyboard-focusable non-static items (`[attr.tabindex]` resolving `0`), arrow-key move / Shift+arrow resize (`handleKeydown` emits a synthetic `dragstart`+`dragend` or `resizestart`+`resizeend` pair via the eventBus, so compaction/collision/`multiSelect` group-move handling applies identically to keyboard and mouse input), `role="group"`, `aria-roledescription`, and `aria-describedby`-linked move/resize instructions. A real, confirmed gap existed here until it was fixed: no `tabindex` binding of any kind existed on this component before, despite `GridLayoutComponent`'s own doc comments already claiming otherwise. See [Accessibility scope](/angular/guide/project/accessibility/) for the full writeup.

## Security

Not zero runtime dependencies (see [Runtime dependencies](#runtime-dependencies) above — `tslib` is a real, if minimal, dependency), but no known reason for concern there specifically. `ci.yml`'s own `audit` job runs a blocking production-dependency audit and a license-allowlist check on every push/PR, covering this package. No `eval`/dynamic code execution found in a direct read of this package's own drag/resize/eventBus logic.

## Browser/runtime support

Node engine range (`^18.0.0 || ^20.0.0 || >=22.0.0`) declared in `package.json`, matching Vue/React, and exercised directly by `ci.yml`'s own `verify` job across all three. Browser support itself isn't independently re-verified in this pass — and, per [Testing depth](#testing-depth) above, isn't backed by an e2e suite the way Vue/React's own browser coverage is.

## Known, open, and deliberately deferred

This package now has its own dedicated [Roadmap](/angular/guide/project/roadmap/) — see that page for the current, accurate list. The concrete, still-open gaps from this checklist specifically: no e2e suite exists yet; the `check:bundle-size` script measures the whole npm package rather than just the runtime bundle (a real methodology fix, not just a number to update); the `check:package-install` smoke test has never been confirmed to pass; and there's no ESLint setup at all for this package.
