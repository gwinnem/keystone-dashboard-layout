description: What keyboard and screen-reader support Keystone Dashboard Layout for Angular actually provides — and what it deliberately doesn't (yet).
---

Same scope and reasoning as the Vue port's own
[Accessibility scope](/vue/guide/project/accessibility/) — this page
documents this package's own implementation specifically, confirmed
directly against `grid-item.component.ts`'s own source.

## What's implemented

### Keyboard move and resize

Every non-static, editable `GridItemComponent` is keyboard-focusable
(`[attr.tabindex]` resolves `0`) and operable:

- **Arrow keys** move it by one grid unit, if it's draggable.
- **Shift + arrow keys** resize it by one grid unit, if it's resizable.

Each keypress is treated as a complete, atomic gesture — `handleKeydown`
emits a synthetic `dragstart` immediately followed by `dragend` (or
`resizestart`/`resizeend`) via the eventBus, the same two calls a real
mouse gesture's start and release would produce, so
`GridLayoutComponent`'s own compaction/collision/`multiSelect`
group-move handling applies identically regardless of which input
method triggered the change. This two-call shape (not just a single
synthetic `dragend`) is a real, confirmed fix in this port's own
history — an earlier version emitted only `dragend`, which meant a
keyboard-driven move of a selected item never brought the rest of the
`multiSelect` selection along with it, since the group-move snapshot is
taken at `dragstart` specifically.

**Works with `multiSelect`'s group move/resize too** — see
[Multi-select & group move/resize](/angular/features/) for the feature
overview.

**Deliberately scoped to single-unit steps**, not a full
[WAI-ARIA grid](https://www.w3.org/WAI/ARIA/apg/patterns/grid/) or
[application](https://www.w3.org/WAI/ARIA/apg/patterns/) widget pattern.
This library isn't a traditional data grid — it's a freeform draggable
canvas — so the full APG grid pattern doesn't map cleanly onto it.

### Screen reader support

- Each interactive item gets `role="group"` and
  `aria-roledescription` (default `"Draggable, resizable item"`), so a
  screen reader announces it as something other than a plain, silent
  `<div>`.
- `aria-describedby` points to a visually-hidden instructions string
  ("Press arrow keys to move." / "Press shift plus arrow keys to
  resize.", each only included if that action actually applies to the
  item) — discoverable on focus, not a mandatory upfront announcement.
- A visible focus outline, so a keyboard user can actually see which
  item currently has focus.

A real, confirmed gap existed here until this was implemented: despite
`GridLayoutComponent`'s own `scrollToItem`/`focusItem` doc comments
already claiming items "get `tabindex='0'` via `GridItemComponent`'s
own host bindings," no `tabindex` binding of any kind existed on this
component beforehand — confirmed via a direct grep turning up zero
matches. `focusItem()` calling `.focus()` on a genuinely non-focusable
element was a real, silent no-op in any actual browser.

### A deliberate, non-obvious design decision worth calling out

Keyboard move/resize **ignores `dragAllowFrom`/`dragIgnoreFrom`/
`resizeIgnoreFrom`** entirely — `handleKeydown` reads only
`resolvedIsDraggable`/`resolvedIsResizable` and never touches any of
the three. Those fields restrict which DOM element a *mouse* drag/
resize gesture can originate from, which doesn't map onto keyboard
interaction at all. A keyboard user who focuses the item gets full
move/resize access regardless of whether a mouse user is restricted to
a specific handle — intentional, matching the Vue/React ports' own
identical reasoning.

### Maximize and restore

The built-in maximize button (`showMaximizeButton`) is a real
`<button type="button">`, so it is reachable with Tab and operable with
Enter or Space. Its text is a visually-hidden label that reads
"Maximize" and, while its item is the maximized one, "Restore" — both
overridable through `ariaLabels` (`maximizeButton`/`restoreButton`).

**Escape restores.** With focus anywhere inside the grid, Escape puts
every item back — unless something inside the item (a dropdown or a
dialog closing, say) already handled that key press, in which case it is
left alone. Escape does nothing when no item is maximized, and a focus
outside the grid does not trigger it.

**Clicking the button moves focus onto it.** Safari does not focus a
button when it is clicked, so without this a mouse user there would
maximize an item and find Escape dead until they tabbed into the grid.
The button keeps focus when the same click restores the item. Maximizing
through `maximize()` or the `maximizedItem` input leaves focus where it
was: the grid does not take it from something else on the page.

While an item is maximized it is neither draggable nor resizable, and the
other items are hidden (`display: none`), so they are skipped by Tab and
by screen readers until you restore.

### Localizable ARIA strings

The close button's label, `aria-roledescription`, and the keyboard
move/resize instructions are all overridable rather than hardcoded
English literals, via the same `IGridAriaLabels` interface Vue and
React use — see [ARIA labels](/angular/api/interfaces/aria-labels/).
The maximize button's two labels are overridable the same way.

## What's not covered (tracked, not silently ignored)

- **No roving-tabindex grid navigation.** Tabbing moves through items in
  DOM order, the same as any other focusable elements on a page.
- **No keyboard equivalent for the drag-from-outside / drag-between-grids
  features** — those are consumer-level example code, not library
  internals.
- **Not independently audited against WCAG success criteria** or run
  through an automated tool (axe, Lighthouse, etc.).
- **Color contrast and the default item styling generally** haven't
  been reviewed.

## Verifying this

`grid-item.component.spec.ts` covers keyboard-accessibility scenarios
at the unit level, including focus attributes present/absent correctly
based on static/edit-mode state, arrow-key movement, and shift+arrow
resize. `e2e/keyboard-accessibility.spec.ts` covers the same ground in
a real browser — a focused item moving/resizing via real key presses,
Tab reachability, and a non-arrow key press correctly doing nothing —
part of this package's own real Playwright e2e suite; see
[Testing philosophy](/angular/guide/project/testing/) for the full
coverage table.
