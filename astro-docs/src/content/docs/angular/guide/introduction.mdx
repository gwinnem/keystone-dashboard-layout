Keystone Dashboard Layout for Angular is an Angular component library for
building draggable, resizable, responsive dashboard grids — the kind of
UI you'd use for a customizable analytics dashboard, a widget board, or
any screen where users rearrange content themselves.

It's a TypeScript-first library built on the exact same shared
`@keystone-dashboard-layout/core` algorithms and native, Pointer
Events-based drag/resize engine the Vue and React packages use — all
three frameworks share one implementation of the hard, easy-to-get-
subtly-wrong parts (collision, compaction, responsive breakpoint math)
rather than each maintaining their own copy. Angular has reached full
feature parity with both.

## What you get

- **`GridLayoutComponent`** (selector `kdl-grid-layout`) — the
  container. A **fully controlled** component: it never mutates the
  `layout` array (or any item in it) you pass in — every drag/resize
  tick (and the compaction that follows it) is reported via a
  `layoutChange` `@Output()` with a brand-new array. The same
  controlled-data-flow contract the React package uses, rather than
  Vue's own two-way `v-model:layout` binding.
- **`GridItemComponent`** (selector `kdl-grid-item`) — a single
  draggable/resizable cell. Unlike the React package, position and
  size are this component's **own direct `@Input()`s** (`i`/`x`/`y`/
  `w`/`h`, all required) rather than fields read off a matching layout
  item — you bind each one explicitly in your own template's `@for`
  loop, the same shape Vue's own `GridItem` uses.
- **Public imperative methods on `GridLayoutComponent`** — reached via
  a template reference variable (`#grid` + `@ViewChild`), the Angular
  equivalent of Vue's `defineExpose`'d template-ref methods or React's
  `ref`-based imperative handle: `compactNow()`, `rearrange()`,
  `duplicateItem(id)`, `undo()`/`redo()`, `selectItem()`/
  `clearSelection()`, `alignSelected(edge)`/`distributeSelected(axis)`,
  `exportLayoutAsSvg()`, `scrollToItem(id)`/`focusItem(id)`, and more.
- **`GridLayoutStorageService`** and **`GridLayoutPresetsService`**
  (both `providedIn: 'root'`) — injectable services wrapping layout
  persistence (serializing to/from `localStorage`) and named layout
  presets. Unlike Vue's ref-bound composables, every method here
  takes/returns a plain layout value directly — you call `save()`/
  `load()` from wherever you already own your own `layout` state.
- **`GridItemHeaderDirective`** — a marker directive
  (`[kdlGridItemHeader]`) applied to your own header content, letting
  `GridItemComponent` project it into a dedicated header region instead
  of its plain default content.

There's also a real, exported close-button component
(`GridItemCloseButtonComponent`) and drag-handle component
(`GridItemDragHandleComponent`), matching Vue and React — useful when
you want those same building blocks rendered somewhere other than
`GridItemComponent`'s own built-in rendering (e.g. inside a custom
header). Most consumers should reach for the simpler, built-in path
first though: a close button is a built-in, per-item opt-in
(`showCloseButton` + a `removeItem` `@Output()` you handle yourself),
and any part of an item is a drag handle by default, restrictable via
`dragAllowFrom`/`dragIgnoreFrom`.

## How it fits together

```ts
import { Component } from '@angular/core';
import { GridLayoutComponent, GridItemComponent } from '@keystone-dashboard-layout/angular';
import type { TLayout } from '@keystone-dashboard-layout/core';

@Component({
  selector: 'app-dashboard',
  standalone: true,
  imports: [GridLayoutComponent, GridItemComponent],
  template: `
    <kdl-grid-layout [layout]="layout" (layoutChange)="layout = $event">
      @for (item of layout; track item.i) {
        <kdl-grid-item [i]="item.i" [x]="item.x" [y]="item.y" [w]="item.w" [h]="item.h">
          Item {{ item.i }}
        </kdl-grid-item>
      }
    </kdl-grid-layout>
  `,
})
export class DashboardComponent {
  layout: TLayout = [
    { i: 'a', x: 0, y: 0, w: 2, h: 2 },
    { i: 'b', x: 2, y: 0, w: 2, h: 2 },
  ];
}
```

`layout` is a plain array of `{ i, x, y, w, h, ... }` objects. You own
that array; `layoutChange` hands you a new one every time the user
drags or resizes something, and you decide what to do with it (usually
just reassigning your own field, as above). `GridItemComponent` itself
still needs `x`/`y`/`w`/`h` bound explicitly per item — this component
doesn't read them off `layout` automatically the way React's `GridItem`
does. Everything else (collision resolution, compaction, responsive
breakpoint switching) happens automatically based on the props you set
on `GridLayoutComponent`.

## Design goals

A few decisions that shape how the library behaves, worth knowing up
front:

- **You own the data.** `layout` is a plain, serializable array you
  control — the library never mutates it in place, only ever hands you
  a new one via `layoutChange`.
- **Sensible defaults, explicit overrides.** Most behavior (draggable,
  resizable, bounded, etc.) can be set once on `GridLayoutComponent`
  and inherited by every item via a DI-scoped event bus, or overridden
  per-item when needed.
- **Idiomatic Angular, not a literal Vue-to-Angular transliteration.**
  Vue's `provide`/`inject` eventBus becomes an injectable,
  component-scoped `GridEventBusService`; its composables become
  `providedIn: 'root'` services; its named slots become a marker
  directive (`GridItemHeaderDirective`) queried via `@ContentChild`;
  and its reactive two-way binding becomes the standard `@Input()`/
  `@Output()` pattern — the same underlying behavior, expressed the
  way Angular actually works.
