Two independent test layers.

## Unit & component tests — Vitest

Pure-function tests for the grid math, validators, and helpers, plus
component tests for every Vue component (`GridLayout`, `GridItem`,
`CustomCloseButton`, `CustomDragElement`), all run against jsdom.

```sh
npm run test           # watch mode
npm run test:ui         # Vitest UI
npm run test:coverage   # single run with coverage
```

### Coverage gate

A **90% minimum** (lines, statements, functions, branches) is enforced
over the library's own source, excluding pure type-declaration files
(interfaces/types have no emitted JS to cover) and the demo app. A run
that drops below 90% on any of those four metrics fails — the same gate
CI runs. See [Production readiness](/vue/guide/project/production-readiness/) for the current real numbers.

### Component testing approach

`GridLayout` and `GridItem` are tested together, mounted so that a real
`GridLayout` renders real `GridItem` children in its default slot — the
same shape actual usage takes. This means `$parent` and the eventBus
(see [Architecture](/vue/guide/project/architecture/)) behave exactly as
they do in production, rather than relying on a hand-rolled fake parent.

A few things need mocking, since jsdom can't provide them:

- **`ResizeObserver`** — jsdom doesn't implement it at all. Replaced
  with a no-op stub for most tests; the initial container-width
  measurement is handled separately.
- **The native drag/resize engine's own pointer handling** — real,
  trusted pointer events and native layout aren't something jsdom can
  produce faithfully. Tests invoke the component's actual drag/resize
  handling logic directly (via a small test backdoor the native engine
  exposes for exactly this), rather than trying to simulate a full,
  real mouse gesture through jsdom.
- **Vue's `useSlots()`**, scoped to the `autoHeight`/`autoSize()` test
  file only — the "happy path" of measuring a slot's actual mounted
  element can't be reached through ordinary Vue slot rendering in a
  test, since calling the exposed `slots.default()` imperatively returns
  fresh, disconnected VNodes regardless. This is the one place a
  targeted mock is the only way to exercise that logic at all.

Testing a `GridItem`'s own prop watchers needs a slightly different
mounting approach than testing the root component directly, since
`GridItem` is rendered through `GridLayout`'s slot rather than as the
test's own root — the project's own test helpers mount with the item's
props on a reactive object instead, so mutating that object re-renders
`GridItem` with new props exactly like a real `v-for` over reactive
state would.

## End-to-end tests — Playwright

Browser tests that drive real drag/resize/responsive interactions
against a real demo app, across Chromium, Firefox, and WebKit.

```sh
npx playwright install   # first time only — downloads browser binaries
npm run test:e2e          # headless, all three browser engines
npm run test:e2e:ui       # interactive UI mode, good for writing new tests
npm run test:e2e:report   # open the HTML report from the last run
```

### What's covered

| Area | Covers |
|---|---|
| Basic grid | Static layout renders at the right positions; default draggable/resizable classes are applied |
| Drag & resize | Dragging moves an item and fires the move event; disabling `isDraggable` blocks movement; resizing from the bottom-right edge grows an item |
| Keyboard accessibility | Arrow-key move and shift+arrow resize; boundary clamping; min-size clamping on shrink; a non-interactive item ignores keyboard input entirely |
| Dynamic items | Adding a layout entry renders a new item; the close button removes one |
| Responsive | Shrinking the viewport moves the layout to a narrower breakpoint |
| External drop | Dragging a native element from outside into one of two grids lands it in whichever grid it was released over; releasing away from both grids drops nothing; a single continuous drag swept from one grid to the other leaves exactly one preview; an existing item can also be dragged between grids via `allowCrossGridDrag` |
| Advanced features | Blocked-move feedback (`preventCollision` + a static item), `compactNow()` re-packing a scattered layout, `duplicateItem`, `snapToGrid` magnetic alignment, saving/loading a named layout preset |

### Notes on interaction tests

Drag and resize tests drive real pointer input (mouse down → move in
steps → up) rather than clicking a locator, since the native engine
needs a real sequence of pointer events to recognize a drag/resize
gesture — a single click won't trigger it.

Resize specifically is edge-triggered (grabbing near the item's own
border, not a separate handle element for most cases), so resize tests
grab a point a couple of pixels inside the item's corner rather than
clicking a dedicated handle.

A container-width measurement can settle across more than one render
pass after mount or a view switch — waiting for an item's own
"draggable-ready" class confirms the drag engine's setup has run, but
not that the container's own width measurement has also finished. A
shared "stable bounding box" test helper exists specifically to avoid
reading a position mid-settle, after this was found to affect even
previously-solid tests, not just newly-added ones.

## Manual testing

Neither Vitest nor the e2e suite covers everything. Cross-browser
scenarios with zero automated coverage in this project's current
environment, touch/mobile behavior, and screen-reader scenarios all
need a human in a real browser — tracked in a manual test checklist, run
before a release touching drag/resize/collision logic, or quarterly
otherwise.
