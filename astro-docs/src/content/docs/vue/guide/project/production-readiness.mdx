## Code quality

- **Typecheck clean** — `vue-tsc --project tsconfig.json --noEmit`. A real, substantial bug was found and fixed here: the monorepo split had left `tsconfig.json` without an explicit `rootDir`, so every cross-package `@/core/*` import fell outside TypeScript's auto-computed root, cascading into ~50 `TS6059` errors from one root cause. Fixed by setting `rootDir` to the common ancestor of `vue/src` and `core/src`.
- **Unit/component tests passing** — a real, substantial number of new tests have been added across `vue`/`react`/`core` since the last confirmed count here; re-run each package's own test command for a current total rather than trusting a specific figure from this snapshot.
- **Test coverage** — `core`: **100% statements/branch/functions/lines**, confirmed via a real `vitest run --coverage` pass (up from an earlier snapshot's 99.11%/97.05%/99.27%/99.18% — the remaining gaps were closed file by file: a genuinely redundant conditional simplified away entirely, and targeted tests added for `utils.ts`'s uncovered branches and `native-interaction.ts`'s `requestAnimationFrame`-related races). `vue`'s own coverage figure from the prior snapshot (99.65%/95.05%/99.64%/99.64%) hasn't been independently re-confirmed since — a substantial number of new tests have been added, but re-run `vue`'s own `test:coverage` for a current number rather than trusting the old one.
- **Mutation testing (Stryker)** — a major update since the prior snapshot, which had this as "not re-run": Stryker's own sandboxing initially failed outright for `vue` (its `@/core` alias reaches into the sibling `core` package, invisible to Stryker's default per-package sandbox) — root-caused and fixed via monorepo-root invocation, documented in full in `packages/vue/docs/STRYKER.md`. With that fixed, real, confirmed mutation runs now exist for all three of `vue`, `react`, and (newly set up this pass) `core`:
  - **`vue`**: overall mutation score **82.08%**, confirmed via a real run. 7 of 8 composable-level files sit above 80% individually (`useGridItemKeyboard.ts` 97.73%, `useUndoRedo.ts` 95.16%, `useLayoutStorage.ts` 90.57%, `useMultiSelect.ts` 87.84%, `useLayoutPresets.ts` 84.48%, `useCrossGridDrag.ts` 83.08%, `useResponsiveLayout.ts` 81.82%, `useGridItemDrag.ts` 80.34%, `useOutsideDrop.ts` 81.43%) — `useGridItemResize.ts` remains the one holdout at 74.23%, improving steadily each pass but not yet closed.
  - **`react`**: overall mutation score **82.93%**, confirmed via a real run, up from 79.42% at the previous check.
  - **`core`**: mutation testing infrastructure added for the first time this pass (previously nonexistent) — a straightforward setup compared to `vue`'s, since `core`'s own `@/core` alias is self-referential (points to its own `src/`), not cross-package. Actively being improved file by file as of this snapshot; not yet at a stable, final overall number worth quoting here — check a fresh run rather than assume a specific score.
- **Lint** — confirmed real, with a known, quantified number, not just "not re-verified": `eslint`/`eslint-plugin-vue` are genuinely configured, and `.github/workflows/ci.yml`'s own comment states this package "carries ~800 pre-existing issues from before it had a working ESLint config at all" — known technical debt, tracked and visible on every PR (the lint step runs with `continue-on-error: true`, so it's advisory, not blocking), not a silent gap. Current exact count not independently re-run in this pass.
- **`npm audit`** — confirmed covered, not skipped: `ci.yml`'s own dedicated `audit` job runs `pnpm audit --prod --audit-level=high` (blocking) and a broader advisory audit from the monorepo root on every push/PR, covering this package. A blocking production-dependency license check also runs.
- **A real reactivity bug found and fixed**: every item-level prop with the same null-means-inherit pattern (`isDraggable`/`isResizable`/`isBounded`/`showCloseButton`/`enableEditMode`/`useBorderRadius`/`borderRadiusPx`) had a direct watcher re-syncing its resolved value when the prop changed reactively after mount — `resizeHandles` never got one. Found via e2e testing (a demo control toggling it had no visible effect), fixed with the missing watcher plus a regression test.

## CI/CD & repository hygiene

- Three GitHub Actions workflows present: `ci.yml`, `mutation-testing.yml`, `release.yml` — confirmed via a direct read, not just cited from memory.
- **A real, confirmed root cause for every recent CI failure across all three workflows**: `pnpm/action-setup@v4` was given both an explicit `version: '9'` in each workflow file *and* an implicit version via root `package.json`'s own `packageManager: pnpm@11.22.0` field — the action refuses to run at all when both are set and they disagree, failing every job in 7–13 seconds, before checkout even finishes installing dependencies. Confirmed by inspecting real, failed run logs directly ("Multiple versions of pnpm specified"), not inferred. Fixed by removing the hardcoded `version` from all three workflow files, letting the action auto-detect from `package.json` instead — **this fix is a local source change only; it hasn't been pushed, so no workflow has actually re-run with it yet.**
- `mutation-testing.yml`'s own `mutation-test-vue` job's 82.08% figure is confirmed via local runs only — every actual scheduled/on-demand CI run of it has failed at the same pnpm step above, not passed.
- Branch protection and an `NPM_TOKEN` secret for `release.yml` to actually publish — both open, and both need a repo admin (not something fixable from source alone).
- CODEOWNERS and Husky/lint-staged both confirmed wired up correctly.

## Testing depth

- **A full Playwright e2e suite run against real Chromium, Firefox, and WebKit** — a meaningful milestone versus an earlier state where only a workaround Chromium build was reachable at all, with no genuine cross-browser testing possible.
- **Two confirmed, named browser-specific limitations**, each skipped with an inline comment recording why: Chromium-only touch-event simulation (a DevTools Protocol limitation, not this library's own gap), and WebKit's lack of a translation layer for simulating native HTML5 drag-and-drop.
- **One honestly unresolved gap**: an `autoScroll` test fails on Firefox only. Three separate fix attempts ruled out the two most plausible causes (a timing race, a teardown-order race) without finding the actual one — `scrollTop` never advances in Firefox across a full 5-second window despite the drag being confirmed active throughout, and the underlying scroll logic reads as browser-agnostic on inspection. Skipped on Firefox with the investigation history recorded inline, not dressed up as an equivalently-understood platform limitation the way the two above are.
- Visual regression baselines don't exist yet.

## Accessibility

Deliberately *not* a full WAI-ARIA grid/application widget pattern — see [Accessibility scope](/vue/guide/project/accessibility/) for the intentional scope limit.

## Security

Zero runtime dependencies is the strongest possible position on third-party runtime-dependency risk here. No `eval`/dynamic code execution anywhere in the library's own source. No telemetry, analytics, or network calls of any kind.

## Browser/runtime support

Node engine range (`^18.0.0 || ^20.0.0 || >=22.0.0`) declared and respected. Browser support relies on `ResizeObserver` and modern-but-broadly-supported CSS — no explicit browserslist-driven compatibility test independently confirms the exact minimum supported browser versions beyond what the `browserslist` config declares.

## Known, open, and deliberately deferred

Genuinely unimplemented as of this snapshot — see the [Roadmap](/vue/guide/project/roadmap/) for the fuller, current version of this same list: swap-on-drag collision mode, sub-grid nesting, an open pluggable positioning-strategy interface, spacing guides with distance labels, per-input-type drag-activation thresholds, async persistence backends, a fast/large-layout compactor, a worker-based layout engine, and a Nuxt module with a full SSR audit.
