## The grid renders with zero width, or collapses to nothing

`GridLayout` measures its own root element's `offsetWidth` via a
`ResizeObserver`, and only updates its internal width `if (offsetWidth >
0)` — a guard against the well-known case where `offsetWidth` reads `0`
while an element (or one of its ancestors) has `display: none`, is
`v-if`-false, or hasn't been laid out yet. When that guard fails, the
grid doesn't error — it silently keeps whatever width it last measured
(or never measures at all), which looks like a frozen or collapsed
layout with no console output to explain why.

Most common causes:

- Rendering `GridLayout` inside a `v-if`-gated tab/panel/modal that
  starts hidden. Prefer `v-show` (keeps the element in the layout tree,
  just visually hidden — width becomes measurable the instant it's
  shown) over `v-if` for anything containing a grid, or force a
  re-measure (e.g. `nextTick` + a resize-triggering change) right after
  the panel becomes visible.
- A flex/grid parent that hasn't completed its own layout pass on the
  same tick the grid mounts. Give the grid's parent container an
  explicit width or `min-width` rather than relying on content-driven
  sizing.
- The container has no defined height and depends on the grid's own
  content to size it, while the grid depends on the container for
  width — a sizing cycle that resolves to zero either way.

## Dragging doesn't start on some (or all) items

If a `GridItem` sets `dragAllowFrom`, that selector is checked
**first, and exclusively** — a pointer-down target that doesn't match
it is rejected outright, and `dragIgnoreFrom` never even gets
evaluated. A `dragAllowFrom` selector that doesn't match anything on
that item (a typo, or markup that changed after the selector was
written) silently disables dragging for the whole item — there's no
warning, since from the library's perspective this is working as
configured.

Check, in order:

1. Is `dragAllowFrom` set on this item? If so, does the selector
   actually match an element that exists inside it right now?
2. Is `isDraggable` `false` on this specific item, overriding the
   grid-wide default?
3. Is the grid-wide `isDraggable` prop itself `false`?

## Responsive breakpoints don't switch when I expect them to

Breakpoint resolution is driven by the grid **container's own measured
width** (the same `ResizeObserver`-sourced value from the section
above) — never `window.innerWidth`. This is deliberate and correct for
grids embedded in a sidebar, iframe, or any container narrower than the
viewport, but it means the zero-width failure mode above has a second
symptom: if the container never gets a real measured width, breakpoint
switching doesn't run either, since it's derived from the same stuck
value.

## Server-side rendering (Nuxt / SSR)

The `GridLayout` component itself has no explicit SSR guard, but it
also doesn't need one: the `ResizeObserver` and pointer-event listeners
are only ever created inside `onMounted`, which Vue's own SSR contract
guarantees does not run during server rendering. The pieces that *do*
carry explicit `typeof window !== 'undefined'` guards are the
optional layout-persistence and layout-preset composables
(`useLayoutStorage`, `useLayoutPresets`) — safe to call during SSR,
they simply no-op until the client takes over.

## `Invalid parameter ...` / `Layout is not valid` errors

These come from the core validators (`layoutValidator`,
`keysValidator`, `marginValidator`, `breakpointsValidator`) rejecting
malformed input before it reaches the rendering/collision logic. The
message names the actual problem — a few worth knowing up front rather
than debugging from the message alone:

- **`Layout can not be empty`** — an empty array was passed as the
  initial `layout`; render nothing (or a placeholder) until you have at
  least one item, rather than passing `[]`.
  - **`Layout is not valid`** / **`Invalid parameter layoutItem id
  passed`** — every item needs a unique, stable `i`; duplicate or
  missing ids fail here.
- **`Invalid parameter cols passed`** / **`Parameter cols must be
  greater than 0`** — `colNum` (or a responsive breakpoint's own column
  count) resolved to `0` or a non-number, usually from a computed value
  that hasn't initialized yet.
- **`Invalid parameter marginPx passed`** — `margin` expects a `[x, y]`
  pixel tuple, not a CSS string like `"8px"`.
