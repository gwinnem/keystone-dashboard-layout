# Security Policy

## Supported versions

This is a monorepo with three independently-versioned framework
packages — [`@keystone-dashboard-layout/vue`](./packages/vue),
[`@keystone-dashboard-layout/react`](./packages/react), and
[`@keystone-dashboard-layout/angular`](./packages/angular) — plus the
shared, framework-agnostic [`@keystone-dashboard-layout/core`](./packages/core)
each of them depends on. Each publishes a single, continuously-updated
major version line; there is no long-term-support branch for older
versions of any of them. Security fixes are released as a new patch/
minor version of the affected package(s) on top of the latest release.
Upgrading to the latest published version of the affected package is
the supported way to receive a security fix. See that package's own
`CHANGELOG.md` (generated by `semantic-release` — doesn't exist until
that package's first release under its current name has actually run)
for release history.

## Reporting a vulnerability

**Please do not open a public GitHub issue for a security vulnerability.**
A public issue gives anyone using this library in production advance
notice of an exploitable problem before a fix is available.

Instead, report it privately using
[GitHub's private vulnerability reporting](https://github.com/gwinnem/keystone-dashboard-layout/security/advisories/new)
for this repository ("Security" tab → "Report a vulnerability"). If that's
not available or accessible to you, open a regular issue asking for a
private contact channel without describing the vulnerability itself.

Please include, as applicable:

- **Which package is affected** (`@keystone-dashboard-layout/vue`,
  `react`, `angular`, or `core`) and its version.
- A minimal reproduction — a fork of one of the live examples for that
  package is a good starting point (see
  [`CONTRIBUTING.md`](./CONTRIBUTING.md#reporting-bugs--requesting-features)
  for the equivalent guidance on regular bug reports).
- The potential impact as you understand it (e.g. XSS via unsanitized
  layout data, prototype pollution, a ReDoS in a validator).

## What to expect

This is a community-maintained open source project without a dedicated
security team or a service-level agreement on response time. That said:

- You should receive an acknowledgment of your report.
- If the report is confirmed as a real vulnerability, a fix will be
  prioritized over other pending work, and a new version of the
  affected package published via the automated release pipeline (see
  `.github/workflows/release.yml`) once it's ready.
- Credit will be given in the release notes / that package's own
  `CHANGELOG.md`, unless you ask not to be credited.

## Scope

Every package in this repository runs entirely client-side and doesn't
perform network requests, read from `localStorage`/cookies on its own
initiative (the opt-in `useLayoutStorage`/`GridLayoutStorageService`
persistence features are exactly that — opt-in, consumer-triggered), or
handle authentication. The attack surface is primarily:

- **The `layout` array and other props/inputs/slot content a consumer
  passes in.** If you find a way for attacker-controlled layout data
  (e.g. a malicious `i`, `x`, `y`, `w`, `h`, or a crafted
  `responsiveLayouts` object) to cause something worse than a rendering
  glitch or a thrown error — arbitrary code execution, prototype
  pollution, a denial-of-service via pathological input — that's in
  scope, for any of the three framework packages.
- **Supply chain**: each package's own runtime dependencies (as of this
  writing, that's just the shared `@keystone-dashboard-layout/core`
  package for Vue and React, plus `tslib` for Angular — none of the
  three framework packages bundle a third-party drag/resize library;
  see each package's own `NOTICE.md` for the complete, current list)
  and the `pnpm audit --audit-level=high` gate in CI (see
  `.github/workflows/ci.yml`) that watches them.

Out of scope: vulnerabilities that require the consumer's own
application to already be compromised, or that only affect the
documentation site (`astro-docs/`) or the internal demo/sandbox/example
apps (`packages/*/demo/`, `packages/*/sandbox/`, `angular-examples-app/`),
none of which are published or run in any consumer's own environment.
